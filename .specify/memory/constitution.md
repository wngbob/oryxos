# OryxOS 章程

## 核心原则

### I. 库优先

每个功能都必须以独立库的形式起步。库 MUST(必须)自包含、可独立测试并有文档说明。
每个库都必须有明确的用途 —— 不允许存在仅用于组织归类的库。
理由:强制功能以库的形式存在,可保持系统的可组合性,并使每项能力在接入整体之前
都能被独立测试。

### II. 命令行接口

每个库都必须通过命令行接口暴露其功能。文本输入/输出协议:stdin/参数 → stdout,
错误 → stderr。MUST 同时支持 JSON 和人类可读两种输出格式。
理由:统一的文本协议让每项能力都可脚本化、可检查、可调试,无需定制工具。

### III. 测试先行(不可协商)

测试驱动开发为强制要求:先编写测试,经评审与批准,确认测试失败,然后才允许编写
实现代码。MUST 严格执行"红-绿-重构"循环;任何实现代码若无驱动其产生的失败测试,
一律不得交付。

### IV. 集成测试

每个接缝处都必须有集成测试:新库的契约测试、既有契约的变更、模块间与服务间通信、
共享数据模式。仅通过单元测试不满足本原则 —— 功能的契约被端到端验证之后,该功能
才算完成。

### V. 可观测性与简洁性

必须使用基于文本的 I/O 与结构化日志,以便在接近生产的环境中检查与调试系统行为。
从简单方案起步并遵循 YAGNI 原则:在没有被证实的需求之前,不得引入任何抽象、依赖
或功能;任何复杂性 MUST 在功能计划中给出正当理由。
理由:可观测的系统才是可运维的系统;简单的系统才能保持可观测。

### VI. 文档面向双重读者

项目中生成的所有文档(规格说明、澄清、计划、任务、代码注释、README 等)同时面向
AI 与人类用户两类读者,因此 MUST 对人类读者友好:结构清晰、语言明确、术语统一、
段落简短,避免只有机器才能解析的冗余格式;当机器可读性与人类可读性冲突时,在不
破坏自动化处理的前提下,人类可读性优先。
理由:文档是人类与 AI 协作的接口。人类读不懂的文档无法被评审、批准和维护,AI
生成内容的正确性也无从校验 —— 双重可读是本项目一切交付物成立的前提。

## 附加约束

- 技术栈、语言/工具版本以及第三方依赖 MUST 在规划开始之前记录于功能规格说明中;
  引入新依赖时,必须对照原则 V 给出明确理由。
- 安全基线:机密信息 MUST NOT(不得)提交进版本控制;跨越信任边界的输入 MUST
  经过校验;当许可证或合规要求存在差异时,以最严格者为准。
- 性能目标如与某功能相关,MUST 以可度量的验收标准形式写入该功能的规格说明,
  而非事后补定。

## 开发工作流

- 所有工作遵循 Spec Kit 流程:规格说明 → 澄清 → 计划 → 任务 → 实现。
  规格说明获批之前 MUST NOT 开始实现。
- 每次 Pull Request 或评审 MUST 核验对本章程的符合性;除非存在已批准的章程修订
  或有书面记录的例外,违规即阻止合并。
- 合并前的质量门禁:全部测试通过(依据原则 III–IV 的单元测试与集成测试)、
  契约均已覆盖测试、可观测行为(日志、CLI 输出)与规格说明一致。

## 治理

本章程的效力高于项目中的其他一切实践与约定。

- 修订程序:任何变更都需要书面提案、项目维护者批准;若影响既有工作,还须随修订
  一并记录迁移计划。
- 版本策略(语义化版本):MAJOR 用于不向后兼容的治理变更,或原则的移除/重新定义;
  MINOR 用于新增原则或章节、或对指导内容的实质性扩充;PATCH 用于澄清、措辞及
  其他非语义性修订。
- 符合性审查:在每次规格评审、计划评审与代码评审中都要检查章程符合性;对无正当
  理由的复杂性 MUST 予以标记,要么简化,要么明确给出理由。
- 本文件顶部的同步影响报告注释属于审阅临时材料,每次修订后的文件版本提交前
  MUST 将其删除。
